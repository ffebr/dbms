# Отчёт по домашней работе 2 — MongoDB

Реализован каталог ShopCatalog с запросами, отчётом о продажах и транзакционной покупкой. Проверка выполнена 22 октября 2026 года на MongoDB 8.0.30 в replica set `hw2rs` из трёх узлов. Код решения — `solution.js`, стенд и контрольные сценарии — `compose.yaml` и `lab.js`, полный фактический вывод — `results/results.json` в Extended JSON.

## Модель и запросы

`products` содержит один документ на артикул и массив его размеров. Валидатор установлен командой `collMod` в режиме `strict/error`; JSON Schema проверяет обязательные поля, BSON-типы и неотрицательные цену и остатки. Корректный товар принят; строковая цена и отрицательный остаток отклонены валидатором с кодом 121. Уникальность размера внутри одного товара — инвариант записи каталога; контрольный набор его соблюдает.

Поиск использует `$elemMatch`, чтобы размер и достаточный остаток относились к одному элементу `variants`. Поэтому A с `L: 0` и `M: 10` не найден при поиске двух единиц L; после изменения `L` на 2 результат изменился с `[B, C]` на `[A, B, C]`. Дополнительные проверки дали `[A]` для `clothes/M/5`, `[D]` для `accessories/L/3` и `[]` для `clothes/L/99`. Курсор возвращает полные документы, сортируя по `_id`. История фильтрует по `userId` и `status`, сортирует по `createdAt: -1, _id: 1` и ограничивает результат 20 документами. Для `userId: 2500, status: paid` получены 20 заказов от `H24, H25` до `H06, H07`; проверены другой покупатель, статус и отсутствие совпадений. Оба запроса используют простую коллацию для точного сравнения строк с учётом регистра.

Позиции встроены в заказ: их читают и создают вместе с заказом, а цена в позиции фиксирует цену **на момент покупки**. Поэтому изменение текущей цены в каталоге не меняет историю и выручку. История покупателя хранится отдельными заказами, чтобы она могла расти без ограничения размера одного документа и чтобы фильтрация, сортировка и `limit` работали по отдельным покупкам.

## Отчёт о продажах

Агрегация отбирает `paid` в полуинтервале `[from, to)`, разворачивает `items`, группирует все размеры по `sku`, суммирует количество и Decimal128-выручку как `qty × items.price`, берёт пять лидеров по выручке (при равенстве — по `sku`) и добавляет название через `$lookup` к `products`. Финальная сортировка закрепляет порядок после соединения. Для января 2026 года получены: A — 3 шт., 320.00; B — 4 шт., 320.00; C — 3 шт., 270.00; D — 2 шт., 240.00; E — 1 шт., 200.00. Например, A состоит из двух единиц по 100.00 в `sale-start` и одной по 120.00 в `sale-middle`: `2 + 1 = 3`, `2 × 100.00 + 1 × 120.00 = 320.00`. Заказ на нижней границе включён, на верхней — исключён; `created` и `cancelled` не участвуют. После смены текущей цены A на 999.00 результат остался прежним.

## Индекс и план

Индекс `{userId: 1, status: 1, createdAt: -1, _id: 1}` ставит поля равенства перед полями сортировки. Направления двух последних полей совпадают с запросом истории, включая порядок заказов с одинаковой датой. В `historyCursor` нет `hint`: MongoDB выбрала план сама. До индекса получены `COLLSCAN` и отдельная `SORT`; после создания индекса — `IXSCAN` без отдельной `SORT`. Индекс занимает место и добавляет работу при записи и изменении заказов.

| План | nReturned | totalKeysExamined | totalDocsExamined | Отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10 000 | да |
| После индекса | 20 | 20 | 20 | нет |

Полные планы находятся в `results/results.json` → `scenarios.index.artifacts.explain-before` и `explain-after`. Там же `index.beforeIds` и `index.afterIds` показывают неизменность выдачи и порядка.

## Покупка и откат

`purchase` использует предоставленную оболочку `transaction`: одна сессия, `readConcern: snapshot`, чтение с primary и `writeConcern: {w: "majority", j: true, wtimeout: 10000}` для commit. Внутри транзакции сначала ищется заказ по `operationId`. При повторе сравниваются `userId` и упорядоченные тройки `sku`, `size`, `qty`; возвращается исходный заказ с его датой и ценами. Изменение любого из этих параметров даёт `REQUEST_CONFLICT`.

Для новой покупки каждое списание — `updateOne` с одним `$elemMatch` на размер и `stock >= qty`, затем `$inc` только найденного варианта. Это условие защищает от недостаточного остатка в самой записи. После успешного изменения берётся текущая цена товара; заказ создаётся с `status: created`, текущей BSON Date, количеством как int32 и ценой как Decimal128. При отсутствии товара, размера или запаса выбрасывается `ITEM_UNAVAILABLE`. Оболочка вызывает `abortTransaction`, отменяя первое списание, если второе не удалось. Сценарий сохраняет `trace` настоящих результатов обновлений: для отката сначала видно `modified: 1` у A, затем отказ B и неизменные остатки после abort.

Атомарность означает, что оба остатка и заказ становятся видимы вместе или не меняются вообще. Идемпотентность повторного бизнес-запроса — отдельное свойство: проверка сохранённого `operationId` предотвращает повторное списание после успешного commit. Уникальный `_id` заказа также защищает от двух документов с одним идентификатором. Комплект проверяет последовательный повтор после подтверждённого commit; общий протокол разрешения неопределённого исхода commit здесь не реализован.

Полные снимки `serverStatus().transactions` до и после успешной покупки и отката, а также `host`, `pid`, `uptime`, `localTime` и разности `totalStarted`, `totalCommitted`, `totalAborted` сохраняются в `transactions-success` и `transactions-rollback` внутри результатов сценария `purchase`. Счётчики принадлежат процессу MongoDB и дополняют сравнение документов и код транзакции.

В сохранённом опыте для успеха разности равны `+1, +1, 0`, для отката — `+1, 0, +1` соответственно. После успешной покупки A/M изменился с 10 на 8, B/L — с 5 на 4; повтор и конфликт не изменили остатки.

## Смена primary

Сценарий записал документ с majority и journal, вызвал `replSetStepDown`, дождался нового primary, затем тем же объектом клиента прочитал старый документ и сделал новую подтверждённую запись. В последнем прогоне primary сменился с `m2` на `m1`; обе записи получили `acknowledged: true`, старый документ прочитан. Адрес подключения содержит seed list трёх узлов и `replicaSet=hw2rs`; драйвер отслеживает топологию и выбирает новый primary, физическое соединение при этом может смениться. Majority-подтверждение означает, что запись приняло большинство узлов. Произвольная secondary может отставать, поэтому её немедленное чтение не обязано показывать самую свежую запись; опыт читал с primary. Роли до и после, подтверждения записей и прочитанный документ сохранены в `scenarios.failover.artifacts.failover`.

## Шардирование

Для ключа шардирования `{userId: 1}` запрос истории с `userId: 2500` направляется только на шард B: значение попадает в диапазон `[2000, 5000)`. Общий отчёт по `status: "paid"` без условия на `userId` должен обратиться и к A, и к B, поскольку подходящие заказы могут быть в обоих диапазонах. Внутришардовый индекс `{status: 1}` не изменит число задействованных шардов: он может ускорить отбор `paid` внутри каждого из них, сократив просмотр документов. Маршрутизацию определяет условие по ключу шардирования и карта диапазонов.

## Воспроизведение и источники

Для запуска нужен Docker с Compose v2 и доступом к образу `mongo:8.0.30`. Стенд использует закрытую сеть Compose; база `hw2` содержит каталог и заказы, база `hw2_failover` изолирует опыт со сменой primary. MongoDB на хосте не требуется.

```sh
docker compose up -d
docker compose run --rm lab fixtures
docker compose run --rm lab all
docker compose down
```

Команда `all` последовательно готовит данные и выполняет сценарии `data`, `index`, `purchase`, `failover`. Каждый сценарий можно запустить отдельно через `docker compose run --rm lab <имя>`. Команда `reset` восстанавливает 6 товаров и 35 заказов, `reset index` — набор из 10 000 заказов. `results/results.json` содержит ответы запросов, ошибки валидатора, полные планы `explain`, состояния заказов, снимки счётчиков и роли узлов. Для очистки учебных томов: `docker compose down -v`.

Автоматический показ кода и результатов запускается одной командой из PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\show-demo.ps1
```

Скрипт поднимает стенд, выполняет `all`, проверяет статусы и соответствие результатов текущему `solution.js`, затем выводит восемь разделов подряд без пауз и останавливает стенд. Все разделы остаются в истории терминала. Для просмотра уже сохранённого прогона без Docker есть параметр `-SkipRun`. На экране выводятся данные из `results/results.json`, поэтому роли primary при новом прогоне могут отличаться от приведённых выше.

Использованы темы лонгридов курса: неделя 4, §3.3 и §3.6 для валидации и `$elemMatch`, §4.1–4.2 для модели заказа, §6.3 и §6.8 и раздел 7 для индекса и `explain`, §8.1–8.2 для отчёта; неделя 5, §3–6 для replica set и транзакции, §7.2–7.4 для маршрутизации шардов.
